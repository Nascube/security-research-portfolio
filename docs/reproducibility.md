# Reproducibility Policy

Reproducibility is a first-class deliverable in this repository. A project
that produces a result nobody else can reproduce is, for the purposes of this
portfolio, an unfinished project.

This document defines the minimum bar every project must meet and the
patterns projects should prefer.

---

## Minimum bar

To be considered "landed", a project must satisfy all of the following:

1. **Pinned versions.**
   - Language version (e.g. `Python 3.11.8`, `Node 22.20.0`).
   - Direct and transitive dependencies pinned via the language's lockfile
     (`requirements.txt` with hashes where practical, `package-lock.json`,
     `Cargo.lock`, `go.sum`, etc.).
   - OS/toolchain assumptions stated in the README.

2. **Deterministic setup.**
   - A single documented sequence of commands sets up the environment.
   - No manual GUI steps.
   - No "download this from a random URL" steps — dependencies come from a
     package manager or are vendored with clear licensing.

3. **One-command primary result.**
   - Wherever practical, a single command reproduces the project's main
     output. Examples:
     - `make repro`
     - `bash scripts/reproduce.sh`
     - `python -m project_name.reproduce`
   - The command exits non-zero on failure.

4. **Explicit inputs and outputs.**
   - Sample inputs live in the project (or are generated by a committed
     script from a documented source).
   - Expected outputs are either committed as fixtures or precisely
     described in the README.

5. **Documented failure modes.**
   - If the project depends on a specific OS, CPU feature, or optional
     dependency, that is stated in the README before the setup section.
   - Known-broken configurations are listed.

6. **A verification step.**
   - At least one automated check — a test, a comparison against a
     committed fixture, or a documented sanity check — confirms the result.

## Preferred patterns

### Environment isolation

- **Python** — use a `venv` or `uv`-managed environment; commit
  `requirements.txt` (or `pyproject.toml` + lockfile). Do not rely on the
  system Python.
- **Node** — commit `package-lock.json`; document the `node --version` used.
- **Rust** — commit `Cargo.lock`; document the toolchain via
  `rust-toolchain.toml`.
- **Containers** — where a lab benefits from strong isolation, ship a
  minimal `Dockerfile` and document `docker build` + `docker run` commands.
  Base images are pinned by digest, not by mutable tag.

### Determinism

- Seed all randomness explicitly and document the seed in the README.
- Avoid depending on wall-clock time in verification steps; use fixed
  timestamps or freeze-time libraries in tests.
- Where floating-point results matter, document the tolerance.

### Data

- Small input data is committed to the repository.
- Large data is generated by a committed script from a documented, stable
  source, with a checksum recorded.
- No project depends on data that can silently change (e.g., a remote CSV
  with no versioning) without recording a hash.

### Reproduction script conventions

- Reproduction scripts live under `scripts/` or the project root.
- They print, at the start, the versions of every tool they will invoke.
- They print, at the end, a clear "OK" line and exit `0`, or a clear
  "FAILED: <reason>" line and exit non-zero.

### Reproducibility section in the README

Every project's README has a section titled **Reproduce** that answers, in
order:

1. Which OS and language versions are supported.
2. How to set up the environment.
3. The single command that produces the primary result.
4. Where to find the expected output.
5. How to run the automated verification.

## When the bar cannot be met

Some projects genuinely cannot be fully reproducible by an outside reader —
for example, because they depend on a proprietary artifact the reader will
not have, or on hardware the reader is unlikely to own. In those cases:

- The project README states the limitation up front, in a section titled
  **Reproducibility caveats**.
- The project ships as much of the pipeline as *can* be reproduced (e.g.,
  synthetic inputs, a mock artifact, or a smaller open substitute).
- The limitation is not hidden inside a setup section that the reader will
  only discover after trying to run the project.

## Regression discipline

- When a change breaks reproduction, the fix and the regression test land in
  the same commit or series.
- When a dependency upgrade breaks a project, the breakage is documented
  in the commit message before the fix.

## Environment attestation

Each project may optionally include an `ENVIRONMENT.md` capturing:

- OS name and version.
- Language and toolchain versions.
- Relevant hardware notes (architecture, memory, GPU/CPU features).
- Date of the reproduction that produced the committed expected output.

This is not a substitute for pinned versions, but it helps future readers
understand what was known to work.
